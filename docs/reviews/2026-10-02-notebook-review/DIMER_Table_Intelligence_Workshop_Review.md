## Executive assessment

The default path is well built. Its data derivation reproduces the hosted run exactly: a CPU re-execution of the
notebook's own §6–§10 cells on the real pinned SciTSR-PD shards selects the same ten canonical tables, in the same
order, as the 2026-09-26 Colab T4 run. Model provenance is pinned and digest-checked, the split is paper-disjoint,
failures are counted rather than dropped, and the opening, roadmap, checkpoints and conclusion template follow the
guided layer closely.

Three Major defects remain. (1) The waterfall's central diagnostic is wrong: a page with no detection is counted as an
**exact** detected-crop grid, so the recorded run reports 9/10 exact detected-crop grids when only 8 of the 9 detected
crops had one. A learner reading the waterfall "top to bottom" is pointed at the wrong stage. (2) The Predict → Change
one thing activity tells the learner to rerun it at 0.98 and 0.30, but after `Run all` the structure model has been
unloaded by §19, so the rerun fails with `NameError`. (3) The BYOD branch keeps its tables and answers in memory and
prints only status counts; pages without OCR rows are skipped silently, the OCR coordinate frame is never stated, and
malformed rows raise bare Python errors.

**Readiness: Needs revision.**

## 3. Findings

### TBL-M1 — Major: a detection miss is counted as an exact detected-crop grid

**Cell/section:** §18 structure metrics (`dimer-table-workshop-36`), §23 waterfall (`-49`), §30 summary (`-66`),
`structure_metrics.csv`.

**Observed issue:** For a page with no detection, `det_crop_objects` is `[]` and the predicted grid is empty, so
`len(gp["rows"]) == len(gold_rows) == 0` and `grid_shape_exact` is `True`. The miss is then counted as an exact
detected-crop grid in the printed mean, in `structure_metrics.csv`, in `waterfall.json` and in the terminal summary.

**Consequence:** The recorded Colab run reports "detected-crop exact grids: 9 / 10" with "hit50: 9". Its per-table
output shows the truth: `1108.4723v1.4` had no detection (`det_crop_pred_shape [0, 0]`) and `1611.09238v1.1` gained a
column (`[4, 6]` against `[4, 5]`), so only 8 of the 9 detected crops had an exact grid. The waterfall therefore reads
9 → 9 → 8, which tells the learner that structure recognition on detected crops lost nothing and that reconstruction
lost a table. That is the wrong stage. It contradicts the notebook's own sample conclusion ("one detected crop whose
grid gained a column") and defeats the "diagnose … by locating the stage" objective.

**Evidence:** Documented execution evidence (2026-09-26 Colab outputs of `-36`, `-49`, `-52`). Direct execution,
probe P01: with one stand-in miss, the miss row has `gold_rows 0, predicted_rows 0, grid_shape_exact true`; 9
reported exact against 8 exact among detected crops.

**Recommended correction:** Score a detection miss as a structure failure on the detected-crop path
(`grid_shape_exact`, `row_count_exact`, `column_count_exact` all `False`), record why (a `status` column:
`ok` / `detection_miss`) and compare detected-crop counts with the gold table's own row/column counts rather than with
reference boxes that may be clipped away. Correct the recorded numbers in `docs/release-verification.md` with a dated
note.

**Acceptance check:** With a stand-in detector that misses one page, `structure_metrics.csv` gives that page
`status = detection_miss` and `grid_shape_exact = False`; `waterfall.json` `structure_detected_crop.grid_exact` is
never larger than `detection.hit50`; with every page detected and every reference grid returned, all ten are exact.

### TBL-M2 — Major: the threshold activity cannot be rerun after `Run all`

**Cell/section:** Activity after §18 (`dimer-table-workshop-37` / `-38`); §19 complex probe (`-40`).

**Observed issue:** The activity tells the learner to set `ACTIVITY_STRUCTURE_THRESHOLD` "(default 0.95; then try 0.98
and 0.30)" and run the cell. Its `grid_counts` calls `recognize_structure`, which reads the global `struct_processor`
and `struct_model`. §19 deletes both ("unload it before TAPAS"). After `Run all`, which is how the notebook says to
start, every rerun of the activity fails.

**Consequence:** The notebook's only Predict → Change one thing → Run → Observe → Explain activity (GDL10, UX6) fails on
its second and third steps with `NameError: name 'struct_processor' is not defined`. The troubleshooting table does
not cover it. A learner who restarts and changes the value before `Run all` also changes nothing canonical, but that
route is not documented.

**Evidence:** Source inspection (`-40` ends with `del struct_model,struct_processor`). Direct execution, probe P02:
the activity cell runs inside the ordered pass, then fails with that `NameError` when rerun after `-40`.

**Recommended correction:** Make the activity self-sufficient: if the structure model is not loaded, the activity
cell loads it from the verified snapshot, runs, and unloads it again, so it works both inside `Run all` and on any
later rerun without disturbing TAPAS's sequential loading. Say so in the activity text.

**Acceptance check:** Executing the activity cell after the §19 cell (model unloaded) completes and prints exact-grid
counts at both thresholds; executing it inside the ordered pass still works; canonical exports are byte-identical with
and without an activity rerun.

### TBL-M3 — Major: BYOD returns nothing the learner can inspect or keep, and its contract is incomplete

**Cell/section:** §28 BYOD (`dimer-table-workshop-59` / `-60`). NOTEBOOK_SPEC DAT12, DAT13, DAT15, DAT19.

**Observed issue:**
1. Results stay in the in-memory `byod_result`; the cell prints only `{'byod_pages': n, 'status_counts': {...}}`. No
   reconstructed table, answer or output file is shown or written (the export cell `-58` runs before BYOD).
2. Pages whose `page_id` has no rows in `ocr.csv`, and files with other extensions, are skipped without a word; a
   folder with no matching pages prints `byod_pages: 0`.
3. The coordinate frame of `x0,y0,x1,y1` (page pixels, top-left origin, unscaled) is not stated. PDF points with a
   bottom-left origin would be accepted and every word would silently land in no cell.
4. A malformed row raises `ValueError: could not convert string to float: 'twelve'` without naming the file, line or
   column; `questions.csv` problems are similar. `BYOD_PATH = ""` produces "BYOD_PATH must contain pages/ and ocr.csv"
   without saying the path is empty.

**Consequence:** The reuse journey ends with no usable result, and two plausible mistakes (missing OCR rows, wrong
coordinate frame) fail silently. DAT15 requires the same output contract as the sample path; DAT19 requires
actionable validation failures.

**Evidence:** Source inspection; direct execution, probe P03 (stand-in models, one synthetic page with OCR plus one
without): status counts only, the page without OCR is not reported, no files written, raw `ValueError` for a bad
coordinate.

**Recommended correction:** State the OCR coordinate frame and limits before the form is used; validate `ocr.csv` and
`questions.csv` row by row with the file, line and field named; report every skipped page with its reason; print each
page's reconstructed table and answers; write `byod/byod_results.json` plus one CSV per reconstructed table under
`OUTPUT_DIR`; reject a BYOD folder in which no page has OCR rows.

**Acceptance check:** A valid synthetic BYOD folder yields printed tables and answers and writes
`byod/byod_results.json` and `byod/tables/<page>.csv`; a page without OCR rows is listed with reason
`no_ocr_rows`; a non-numeric coordinate fails with a message naming `ocr.csv`, the line number and the field; an empty
`BYOD_PATH` fails with a message naming `BYOD_PATH`.

### TBL-m1 — Minor: BYOD `accepted_answer` comparison rejects equal numbers

**Cell/section:** §28 BYOD, `exact_string_match`.

**Observed issue:** For an aggregation answer, `predicted` is the float `numeric_answer`, so `norm_cell(12.0)` is
`"12.0"` and an accepted answer of `"12"` is reported as a mismatch.

**Evidence:** Direct execution, probe P05 (`SUM`, numeric 12.0, accepted "12" → `exact_string_match: False`).

**Recommended correction:** Compare numerically within the same `1e-6` tolerance the sample path uses when both sides
parse as numbers; otherwise compare normalized strings. Name the field for what it is (`accepted_answer_match`).

**Acceptance check:** Numeric 12.0 matches "12" and "12.000"; 12.5 does not match "12"; lookup strings still compare
by normalized text.

**Acceptance check:** `waterfall.json["qa"]` contains integer `*_correct` counts that equal accuracy × 50; the §23 note

### TBL-m4 — Minor: the "trace a box through page → crop → table frames" objective has no learner activity

**Cell/section:** Opening objectives (`-00`), §14 crops (`-27` / `-28`). UX1.

**Observed issue:** The translation is implemented (`translate_gold_objects`, `source_cells_in_crop`), but the learner

**Recommended correction:** After building the crops, print one reference row box in the table, page, gold-crop and

**Acceptance check:** §14 prints one box in all four frames, and a checkpoint asks the learner to derive one frame

### TBL-m5 — Minor: the resource table compares unlike latencies

**Cell/section:** §15 (`-30`), §21 / §22, §25 (`-54`). UX12.

**Observed issue:** Detection latency is per page with CUDA synchronisation. Structure "mean_latency_seconds" times a
gold-crop *and* a detected-crop inference together (`mean_pair_seconds`) without synchronisation. TAPAS peak memory is
read without resetting the counter after the structure stage. The three rows look comparable but are not.

**Recommended correction:** Time each structure inference separately with synchronisation, reset the peak-memory
counter before TAPAS, and label the latency unit (per page, per crop, per question) in the table.

**Acceptance check:** The resource rows carry a `latency_unit` field; structure latency is per crop; the source shows a
peak-memory reset before TAPAS scoring.

### TBL-m6 — Minor: some form controls are unchecked or cannot be changed

**Cell/section:** §3 Configuration (`-04`). UX10.

**Observed issue:** `CROP_PADDING`, `GRID_NMS_IOU` and `COMPLEX_STRUCTURE_TABLES` are never validated (a negative
padding crops inside the table). `END_TO_END_TABLES` is a form field, but any value other than 10 raises.

**Recommended correction:** Validate the ranges with messages that name the field and the allowed range; make
`END_TO_END_TABLES` a plain constant with a comment that the QA set is fixed at ten tables.

**Acceptance check:** Out-of-range values of each control raise a `ValueError` naming the control and its range;
`END_TO_END_TABLES` carries no `@param` annotation.

### TBL-m7 — Minor: the spanning-cell probe can leave panels from an earlier run

**Cell/section:** §19 (`-40`).

**Observed issue:** Panels are written into `complex_probe/` without clearing it, so lowering
`COMPLEX_STRUCTURE_TABLES` or disabling the probe and rerunning leaves earlier panels next to the new ones.

**Recommended correction:** Remove earlier `*.png` panels from `complex_probe/` before writing this run's panels.

**Acceptance check:** After a run with 3 tables followed by a run with 1, `complex_probe/` holds exactly one panel.
