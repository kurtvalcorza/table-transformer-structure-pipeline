## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/table_transformer_structure_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 4-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False`. The checkpoint's backbone is an in-library ResNet (`use_timm_backbone: false`), so no timm dependency and no construction-time fetch exist; `use_pretrained_backbone=False` is passed anyway. The pinned `preprocessor_config.json` says `size: {"longest_edge": 800}`, a shape the pinned transformers image processor refuses; the loader passes the equivalent `{"shortest_edge": 800, "longest_edge": 800}` (both caps at 800 → longest edge 800 for every aspect ratio) and the notebook says so. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` writes `outputs/table_transformer_structure_input_manifest.json` with the schema (six labels, 125-query ceiling), the ceilings, the input's observed mode and size, the threshold, the verdict, and one recorded rejection finding from the out-of-range-threshold probe; `evaluation_report` writes `outputs/table_transformer_structure_evaluation_report.json` — `sample-sanity` with one `box_iou` entry per reference box, matched to same-label detections only, on the synthetic crop; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 730×350 crop of an 8×5 ruled table rendered in code with Pillow's bundled font and 10 px of page margin (`UPSTREAM_CROP_PADDING`, the upstream inference script's value) — the same crop the smoke run used; `box_iou` against rows and columns you rendered yourself is sanity evidence for the input contract, forward pass and coordinate mapping, not a recognition metric. The crop digest depends on the Pillow build's bundled font rendering and is printed, not asserted.
- Score semantics (UNC1–UNC4): every `score` is the query's softmax class probability under the model's own head, not a calibration for the deployment's tables; the threshold is a caller-owned request parameter exposed as a `# @param` value with the package default 0.5 (the upstream inference script's per-class value, not a calibration) and passed explicitly on every `recognize` call. The notebook performs no validation of its own — image and threshold are checked only by the pipeline's `validate_inputs`/`recognize` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_DETECTIONS` (125), the six `LABELS` and `UPSTREAM_CROP_PADDING` are printed before the model runs.
- CPU is documented as adequate (card-measured 4.8 s load, 0.12 s per `recognize` on the 730×350 crop; 0.37 s on a 4096×4096 blank image — which returned 23 objects, the "any image yields structure" risk stated in the notebook).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
